# Build & Artifact Governance Standard

Status: **Normative — v4.4**

## 1. Purpose

This standard governs the truth boundary from exact source and build inputs to build outputs and promoted immutable artifacts. It does not own Release Qualification, Distribution publication, Deployment result, or provider-specific packaging mechanisms.

## 2. Authority boundary

Owned here:

- exact source identity used by a build;
- materially relevant build profile, toolchain/runtime and build-input identity;
- build output identity and evidence;
- package/content-policy evidence when material;
- promotion from a build output to an immutable artifact identity;
- non-transfer of prior qualification to rebuilt or changed bytes.

Not owned here:

- dependency/toolchain selection policy — v4.1 Dependency & Toolchain Governance;
- workspace retention semantics — v4.1 Workspace & Artifact Governance;
- publication/channel state — Distribution Governance;
- rollout/execution result — Deployment Governance;
- Release READY/PASS — Release authority.

## 3. Exact build subject

A material build claim MUST bind the exact source revision plus the build profile and toolchain/runtime identities needed to reconstruct what was built. Mutable branch/tag names are insufficient when exact source identity is material.

Materially different build profiles MUST remain distinct build subjects. For example, debug vs release, platform/architecture variants, feature-set changes, signing mode, packaging profile, and toolchain-major changes MUST NOT silently share one build identity when they can alter produced bytes or behavior.

## 4. Build output is not promoted artifact

A successful build produces a build output. The output does not self-promote into a distributable/release artifact merely because compilation or packaging succeeded.

Promotion is a separate evidence-bearing act. Promotion SHOULD bind the exact build/output identity and MUST establish an immutable artifact identity suitable for later Distribution/Deployment/Release references.

Forbidden inference:

```text
build command succeeded -> artifact qualified/promoted
```

## 5. Immutable identity and mutable aliases

Canonical artifact identity MUST identify immutable bytes or an equivalent immutable content identity. Mutable names, filenames, tags, channels, branch names and registry aliases MAY locate an artifact but MUST NOT replace immutable identity.

Forbidden inference:

```text
same tag/channel/name -> same artifact bytes
```

If an alias is repointed, evidence attached to the old immutable identity does not transfer to the new bytes.

## 6. Qualification does not transfer across rebuilt bytes

A rebuild from apparently equivalent inputs can produce new bytes. New or rebuilt bytes MUST NOT inherit prior artifact Validation, Review, Release or Deployment qualification merely because source/tag/version text matches.

Where byte-for-byte reproducibility is material, reproducibility evidence MAY support equivalence. This standard does not impose one universal reproducible-build level or provider mechanism.

## 7. Package/content policy

When a build output is intended for packaging or promotion, the package boundary SHOULD have evidence that material prohibited content is absent. By default, ordinary deliverables MUST NOT accidentally include:

- secret or credential values;
- local caches and temporary build state;
- runtime state/databases unless explicitly part of the product contract;
- Agent/session-only files, prompts or scratch artifacts;
- unapproved private keys/signing material;
- unrelated workspace files.

Project/product profiles MAY define additional allowed/forbidden package content. Such specialization cannot weaken applicable secrets or release authority.

## 8. Evidence and provenance

A useful Build Manifest or equivalent evidence binds, as material:

```text
exact source ref
build profile ref
toolchain/runtime ref
input/dependency refs
commands or workflow identity
output refs / digest facts
content-policy evidence refs
builder/operator provenance
```

Artifact Promotion evidence binds the source build/output to an immutable artifact identity and promotion evidence. Neither object is a Release verdict.

## 9. Fast Path and non-applicability

Changes with no material build/package/artifact effect need not create empty Build/Promotion records. Fast Path reduces ceremony but cannot be used when generated bytes, package contents, public artifacts, platform profiles or build provenance materially change.

## 10. Required forbidden inferences

| Input fact | Forbidden conclusion |
|---|---|
| build succeeded | artifact promoted or Release READY |
| output filename unchanged | immutable bytes unchanged |
| same tag/version string | same artifact identity |
| rebuilt candidate uses same source | old artifact qualification transfers |
| package command succeeded | package contains no secret/cache/runtime leakage |
| artifact exists | Distribution or Deployment succeeded |

## 11. Failure handling

If exact source/profile/toolchain/output identity is unknown, preserve UNKNOWN/BLOCKED in the owning workflow rather than manufacture provenance. If package-content evidence requires unavailable platform tooling, create an exact-subject Validation handoff. Missing real execution is never a PASS.

Provider- or product-specific requirements that cannot be generalized remain profile/project authority rather than becoming universal ADS mandates.
