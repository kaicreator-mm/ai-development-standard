## First-pass Findings That Changed the Standard

The initial draft/reference pack passed basic parsing and rule checks, but review exposed quality problems that would have allowed misleading coverage claims.

### 1. Inert dimensions can fake coverage

The first pack included `supplier_status=unknown` without a domain rule that changed expected behavior. That made the dimension look covered while it had no semantic effect.

**Feedback:** every declared dimension now needs a behavioral/risk rationale. Values that matter to expected behavior must map to a rule/risk; exploratory dimensions must be labeled rather than counted as required coverage.

### 2. “Failure” was overloaded

The first pack mixed unsupported business values, missing business facts and contract-invalid structures under a generic failure label.

**Feedback:** the final taxonomy separates `schema_invalid`, `domain_invalid`, `failure_injection` and adversarial behavior. Intentionally schema-invalid records live in a separate file so a parser/schema failure is not confused with a broken pack.

### 3. Golden set was too weak

The first pack had only two Golden Cases: happy path and missing product. It did not lock the highest-value risk/escalation semantics.

**Feedback:** Golden selection must be risk-driven, not count-driven. The final pack adds canonical blocked-supplier and conflicting-evidence Goldens and requires explicit invariants/allowed variation.

### 4. Reproducibility needed more than a seed

A seed alone does not identify the generator behavior. Generator/library upgrades can change output.

**Feedback:** final metadata records generator version and frozen output hashes. The standard now requires dependency/runtime identity when it can change generated bytes.

### 5. Record count is a weak metric

The first pack could have been expanded with many similar normal records without increasing meaningful risk coverage.

**Feedback:** coverage is reported by risk class, domain rule, boundary and dimension values. Duplicate/near-duplicate inflation is explicitly rejected as evidence.

### 6. LLM-generated expected answers need independent authority

The exercise confirmed that an LLM can create plausible cases and rationales, but that does not make its expected answer authoritative.

**Feedback:** the standard requires Golden expected behavior to map to deterministic rules, approved evidence, an independent reviewer or an established real case. An LLM cannot be the sole generator, oracle and approver.

## Remaining Deliberate Limitations

This reference domain is intentionally small. It does not attempt to demonstrate every possible test-data technique such as:

- large-scale performance distributions;
- time-series/event ordering;
- database referential graph generation;
- image/audio/video fixtures;
- real de-identification pipelines;
- multi-language locale packs;
- hidden-data access controls.

Those are project-specific extensions and should follow the same provenance, reproducibility and validation principles.
