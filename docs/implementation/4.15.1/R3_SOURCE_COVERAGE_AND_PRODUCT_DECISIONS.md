## 2. Proposed Product decisions to independently review (not frozen)

**D-SOURCE / #1259: choose B for v4.15.1 candidate, over A, on utility grounds.** The first-party collector's goal includes failed/interrupted uncommitted Attempts; hiding every such event from a GitHub-only Tally would bias denominator, cost and improvement conclusions. Proposed new opt-in wire permits **observation-only** source-unpinned Attempt (not a Task-source claim) with `source_status=UNPINNED|UNKNOWN`, `source_sha=null`, an explicit reason and source-qualified collector observation, `attempt_binding=COLLECTOR_ONLY` or UNKNOWN, and `verifier.source_sha=null` / `verifier=NOT_RUN|ACK_ONLY|UNKNOWN` only where truthful. Valid unpinned schema must be **machine-rejected as evidence for exact Task/Claim/Gate/currentness/Release**, irrespective of token cost or prose. For known SHA but no actual verifier, keep SHA+UNKNOWN; don't invent fake test. Consumers pinned to prior v4 may only see absence/insufficient evidence, never backfill through private task-meta. This is a Product tradeoff candidate, not yet authorized publishing.

**D-WB / #1234: coexistence, no lowered Review gate.** An actual native PR/Issue Validation evidence writeback is source-owned evidence if selected Validation/Review authority permits native evidence and binds its exact subject/real exits; only a separately admitted canonical `REVIEW_RESULT` can enter the governed §9.2 machine-finding aggregate, and its material findings require records. When selected policy explicitly requires an Event, comment-only evidence does **not** satisfy it. Require the validating session's execution pack/dispatch pointer to carry (a) source-bound target Issue/PR, (b) before-return publication/readback obligation, (c) required evidence format per owner, (d) next receipt receiver. The Validator's summary/chat alone is not GitHub publication. An unpushed local report is NOT_PUBLISHED and must not yield current review/merge success.

**D-KNOW / #1202 + §8: existing-state reuse.** Unverified or partial observations may be used for triage and candidate **proposal** only. Strict Task success requires independently observed applicable semantic acceptance; promotion to approved/selected Procedure/Domain Package and a new BUILD requires the ordinary owning gate/qualification. `Task Learning`, Tally evidence and optional experiment can never self-mint that authority. Existing `NO_CHANGE|MORE_EVIDENCE|OPEN_ADS_INTAKE` must be visible as citation-backed owner disposition, not a new enum/status.

**D-COMPAT: two-dimensional versioning, explicit trial only.** Proposed distinct `ads/github/v5` *report-only profile* is **not** a binary-compatible update of old `ads/github/v4`; its introduction under standards **v4.15.1 patch** needs independent Product + compatibility authority acceptance. Keep old v4 schema blob byte-identical. A v4.15.0 pinned reader/writer MUST continue its v4-only behavior: reject/ignore v5 and never partially interpret it; a v4.15.1 eligible producer/consumer must affirmatively select/report v5 capability under an immutable qualified pin; default existing v4 behavior and v3 Work Item/Intent/Event persist unchanged. New-v5 producer + new-v5 reader passing fixtures is **NOT** proof of old v4 reader accepting v5; rejected-as-unsupported is the required old-window outcome. If project-facing release policy forbids a wire-major new profile inside a standards patch despite explicit opt-in, Product should **split the report wire to later minor release**, while v4.15.1 retains only non-breaking normative #1241/#1234/#1202/Evolution clarifications. Do not silently call this semver issue resolved; required matrix under INTERFACE_COMPATIBILITY_GOVERNANCE_STANDARD §§5–6 and actual consumer windows.

## 5. R3 safety conditions tightened before independent review

**Unpinned observation must be profile-discriminated, not a global nullable source.** New-profile `source_sha=null` is allowable **only** inside a source-unknown `EXECUTION_SUMMARY` with the explicitly observational `attempt_binding=COLLECTOR_ONLY`, typed source status/reason, and no accepted source/Task/Gate authority. It MUST NOT make a `CORRECTION` or `EXPERIENCE_USE_FEEDBACK` source nullable, allow a canonical admitted Dispatch to lose its exact source, or create an authoritative verifier result without an exact tested subject. An attempted `verifier=PASS` or source `currentness=CURRENT` on such a summary is invalid. If an unpinned tool execution reports a failure, record it only as bounded observation with source/limits; never treat it as exact-subject strict validation. Same wire must require real immutable source bindings for authority-bearing evidence as dictated by owning gate.

**Native comment vs §8 terminal event:** `LOCAL_AGENT_HANDOFF_PROTOCOL.md` §8 L146–168 already requires a structured phase-exit event/readback. Merely posting a native Markdown validation comment is **not** an exemption from that pre-existing terminal handoff when applicable. A native comment may hold rich commands/toolchain/exits and be accepted as Validation/Review evidence *if* the actual owning policy permits; the phase terminal canonical Event/handoff still must refer to this evidence and be published where §8 requires it. If `REVIEW_RESULT` is emitted, §9.2 requires machine findings records; no opaque Markdown-to-event upcast. The owner may explicitly decide a different allowed evidence form under existing authority, not by an assistant's inference.
