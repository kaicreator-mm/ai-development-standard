## 1. G1 positive effective-selection/source/currentness contract

**Selection is a source-bound observation/decision, not an Agent entitlement.** The only authoritative Task remains the GitHub Issue + its pinned accepted Task/Execution Pack, dependency and Claim policy; selected executor/provider does not mint a second Claim.

A minimal versioned **effective-selection projection** is held by the existing **Task/Execution Pack/authorized Dispatch owner** (Tally MAY implement it; ADS does not implement that service). It MUST be reconstructible through immutable owner-native Issue/Pack/Dispatch evidence; a private profile API is never the only source of normative currentness. Project adoption and exact accepted ADS revision still follow existing project-local source pin rules. Candidate record references below are *logical requirements*, **not additional required v1 JSON fields or new event kind**:

| Binding | Required evidence / source | Missing, stale or contradictory |
| --- | --- | --- |
| Selection identity | source-owning Issue/Task ref; accepted Task Pack revision; effective selection ID/version; immutable decision/publication receipt; Task/Attempt and current Claim generation/dispatch ref **when this is a protected execution** | `UNQUALIFIED/UNKNOWN`; no protected work |
| Actor and requested role | declarative `operator_kind/operator_id/session_ref` and `actor_role` under GitHub Interaction §5/§8; Role Execution Profile id/version and accepted authority refs | No inference from shared transport login, profile string or self-reported reviewer PASS |
| Profile and constraints | exact immutable Agent Capability Profile id/version/blob or accepted immutable artifact ref, Tool/Skill/Host/runner constraints, Task risk/acceptance/environment and applicable ADS/profile rev | `INELIGIBLE/UNKNOWN`; cannot auto-select a newer/easier profile |
| Observed capability | independently readable Agent Capability Evidence v1 subject/result/observation kind/strength, env, proof date/currentness/validity scope; real runner availability if physical tests needed | Historical proof is not live availability; route unmet capability to CI/LOCAL where eligible |
| Selection/admission owner | source-authorized Task/Dispatch or Pack acceptance record and source-currentness/permission/dependency/resource checks according to existing policy | Mere scheduler intent/prose/Schema-valid comment grants no Claim or Tool permit |
| Re-selection/revocation | reason, actual new immutable selection version, current Task/Claim/dispatch authority, predecessor ref and permitted transition/readback; resume/handoff/supersede when same protected key is active | No last-write-wins or implicit mid-Task profile update; UNKNOWN old Claim ⇒ HOLD |

**Ordering:** `Task accepted/pinned → constraints and observed capability checked → effective selection proposed → authorized Dispatch/Claim admission/currentness checked → selection pinned to accepted work → permitted steps`. When the workflow first creates a read-only selection candidate, it has no mutation/authorization effect. A runtime/currentness check MUST recur at the actual protected operation; a previously valid selection cannot bypass expired or revoked runner, role, scope or Claim. Selecting another Agent never automatically acquires the previous Actor's Claim. Hand over only under source-valid terminal/resume/handoff rules and existing generation/resource discipline. The profile itself never confers access to a Host, repository or Kernel.

**Positive:** A Project has an accepted ADS revision and Task Pack; Builder B's immutable Profile P and applicable observed native Node24 Evidence E match a bounded Task; accepted Dispatch/Claim C and role/runner refs are current and explicitly bind selection S. B MAY perform only C's allowed write set and checks. A later P2 declaration or extra runner feature cannot update S. **Negative:** E is historical on Node22, live runner cannot be verified for Node24 ⇒ physical validation `NOT_RUN/UNKNOWN`, not PASS or blind assignment.

## 2. G2 delegation and Tool/effect outcome contract (independent truth domains)

There are **four independent lifecycle/authority planes**; none is a synonym for another:

| Plane / owner | Stable causal evidence | Can prove | Cannot prove |
| --- | --- | --- | --- |
| **Task / Claim / Review / Gate** — current ADS/GitHub owner | Task/Claim key/generation, accepted actor/role, exact source subject, allowed write set, independent Review/verifier refs | protected source authority, actual accepted Gate if qualified | provider side effect from executor text |
| **Child Dispatch** — existing Execution Architecture §5 and §8 | parent accepted Task/Claim + parent/child Dispatch ids, parent/child logical operator/session/role, effective-selection refs, issue/dependency or bounded same-Task Step, immutable request id/attempt/revision | `QUEUED/DELIVERED/ACKNOWLEDGED/RUNNING/DONE/FAILED/CANCELLED/TIMEOUT/STALE` of the assigned **worker job** | final provider/Business Effect, independent Task PASS |
| **External Tool / Host / DomainHarness Effect** — actual provider or K boundary | intent id, request fingerprint, authorization / K admission where applicable, idempotency capability/key, provider operation id, provider-owned terminal effect receipt/reconciliation proof, source and correlation refs | an actual externally witnessed operation/effect only to the exact receipt's scope | Task-Review/Gate PASS, new Task/Claim authority |
| **Independent verifier / publication** — existing Validation/Review/GitHub owner | exact tested subject, role-independent assessor, native readback, semantic acceptance/coverage, rejected/unproven obligations | verified narrow semantic result, qualified Task Gate only under existing policy | provider Effect beyond observed scope, automatic Package promotion |

**Causal chain (no second workflow):**
`accepted parent Task/Claim → parent Dispatch → bounded child delegated intent (scope/role/tool/host, current selected snapshot) → child admission/Dispatch → Tool/K/Host-authorized operation → effect receipt or unresolved UNKNOWN → child work result → parent reconciled result → exact-source verifier and original Gate → GitHub evidence readback`.

Each edge MUST cite actual immutable source-native IDs. A child inside one protected Task either executes under **explicit bounded single-writer delegated authority of the current accepted Claim** or obtains a **separately permitted non-conflicting Task/Claim** under the existing DAG; it MUST NOT concurrently assume the same protected Writer merely because a parent sent a message. Child Tool rights are the **intersection** of the source-approved Task/Claim/role/selection and actual Host/K/provider authorization, never a union or an inheritance from narrative parent text. Parent cannot delegate greater authority than it holds. An ordinary trusted local helper without external effect or independently delegated task needs no new wrapper.

**Replay/ordering:** Distinguish logical request id, dispatch attempt/retry id and stable provider operation/effect id. Exactly one owner may reconcile a provider idempotency/operation receipt; a duplicate worker callback for the same immutable source event is a delivery duplicate, not additional execution. Distinct physical retries MAY count as separate actual effects; no identity from local counters alone. A late `ACK/DONE` after timeout or cancellation REQUEST is historical Dispatch evidence only: it MUST NOT overwrite a later terminal authority without source/currentness reconciliation. `CANCEL_REQUESTED` is not `EFFECT_CANCELLED`; if the provider might have committed but no qualified terminal receipt is obtainable, status is `UNKNOWN/HOLD`, not retry-safe, not `FAILED` and not `COMPLETE`. A child Dispatch `DONE` means worker completed its bounded job, **not** that its external Effect succeeded or parent passed acceptance. For a non-idempotent operation with lost response, NEVER replay until actual provider-specific idempotency/reconciliation proves safety. Conflicting callbacks/effect receipts or uncertain Claim terminal ownership ⇒ source-bound HOLD and human/owning-controller reconciliation under existing recovery, not synthetic state updates.

**Positive:** Parent Claim C authorizes source-only code; a bounded child under C produces an immutable GitHub PR and exits, with no external Effect. Parent's independent Reviewer still must assess actual SHA. Separately, when a Tool operation is explicitly permitted by Host/K and provider returns an independently verifiable terminal receipt, a worker may report that narrow tool result; Task PASS still requires applicable independent exact-source verifier.
**Negative:** Provider ACK followed by missing final response or cancellation request cannot be converted into terminal Effect, even if Dispatch `DONE`; maintain `UNKNOWN`, refuse repeat. Child lacks source-authorized Tool privilege ⇒ reject *before* tool invocation, preserving refusal/evidence with no effect. Child's own self-reported model ID is not proof of actual provider routing.
