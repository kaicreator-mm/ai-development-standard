## 1. Problem and outcome

ADS v4.14 supplied one declarative `ads/github/v3` Work Item/Intent/Event/Report carrier and shape-only validator with immutable private Task Report manifest pointer; it did **not** implement a real task-meta Report Publisher or Tally GitHub consumer. Existing `report.data` is intentionally narrow and does not by itself give Tally a guaranteed machine-readable Task/Attempt/verifier/metrics/learning summary without opening private task-meta objects.

**Desired v4.15 outcome:** two versioned, stable GitHub interface contracts and one real cross-repository interoperability proof:
```text
Agent/Host execution (actual observations)
    → task-meta capture, correlate, private immutable evidence
    → one bounded, safe ADS GitHub Issue Task Report + actual readback
    → Tally v2 GitHub-only reader (Issue/PR/CI/Review + ADS Report)
    → evidence-derived Task/Attempt/cost/quality/experience assessment
    → Tally source-qualified ADS GitHub use/outcome feedback + readback
```
ADS owns **standard and conformance**, task-meta and Tally own production code in their repositories; GitHub native authorities and DomainHarness K/remote provider effects are not duplicated.

## 2. Explicit Product decisions (proposed for Product Review)

**D01 Scope.** v4.15 is **not** the full #1199 Agent management suite or automatic Domain Package evolution. It covers required task-meta↔GitHub publication and Tally↔GitHub read/feedback. #1200/#1201/#1206 are not globally admitted. Reuse #1198/#1202 only for minimal semantics required by a real Attempt/verifier/use record.

**D02 Carrier — product decision.** Every newly published canonical record retains the **single** first-line `<!-- ads:github -->` Markdown/YAML envelope with `kind: report` and schema-validated **YAML `data`** as the only machine-consumable content. A parsed Markdown header, KEY=VALUE appendix, secondary unvalidated machine projection, or mutated v4.14 `ads/github/v3` `report.data` is **forbidden**. v4.15 introduces a **new explicit schema identity** for its additive machine-readable Report/Feedback shape (target identifier `ads/github/v4`, confirmed/registered by L2 under existing compatibility governance); existing `ads/github/v3` documents and schema remain byte-identical and authoritative for v4.14. The v4 profile reuses the established four outer `kind` families (especially `report`); L2 defines the *minimum* discriminated profile schema, source refs and validator fixtures, not another parallel format.

**Cross-version rule:** A v4.14-pinned **v3-only reader** confronted with new v4 identity MUST **reject cleanly or ignore the unsupported record**, never partially validate by stripping schema/version or unknown fields; it remains on its effective v4.14 pin. A v4.15 reader MUST read historical, unchanged v3 reports **read-only** through the pinned original v3 schema, and classify any required new Task/Agent/Verifier/Cost/Experience fields absent from v3 as `INSUFFICIENT_EVIDENCE`/`UNKNOWN`, not fabricated values or current v4 admission. New normalized writes under v4.15 use only the effective current v4 format; old v3 reports remain immutable historical evidence. L2 establishes precise field-level/wire/behavior compatibility, release and consumer migration proofs for this separate schema identity before implementation.

**D03 No private consumer link.** Tally MUST read **only actual GitHub** (Issue/Dependencies/Claim/PR/CI/Review/ADS comments). It MUST NOT require task-meta API/SDK/DB/raw Trace/private Manifest dereference, even if task-meta stores complete private data. Publisher may keep internal private objects. Missing GitHub-safe detail implies `INSUFFICIENT_EVIDENCE`, never an invisible private bypass. **GitHub-only is tested, not self-attested:** the real Tally reader's effective credentials/environment and permitted endpoint list must be captured in an independently inspectable, secret-redacted execution witness; run it without task-meta secrets/endpoint config and with task-meta/private-manifest egress blocked or provably unavailable. An attempted forbidden lookup must fail and leave the result `INSUFFICIENT_EVIDENCE`. Test credentials and deny logs must not leak secrets.

**D04 Authority.** Telemetry is observational, and ADS schema validation produces only shape validity. GitHub owns Issue/PR/Review/CI actual facts, accepted Claim and permissions. Strict Task/Release PASS requires the existing exact-subject authoritative verifier/Gate; a tool response/ACK, completed Agent Attempt, parsed summary, or partial green checks cannot assert Task PASS. DomainHarness K, applicable C adapter and external Host keep their own actual Effect and remote completion authority.

**D05 Identity/cost.** Report distinguishes Task, Run, Attempt, self-declared logical actor/session/role, exact source/ADS pin, verifier subject/coverage, observed/inferred/self-reported/unknown measurements, duplicate and retry scopes, billed vs estimated cost; missing values remain UNKNOWN, never 0. No GitHub-transport-account operator test. Provider adapters may report a limited capture profile honestly; no universal hooks mandated.

**D06 Writer/reader resilience.** Producer uses stable owning Issue + report_id + revision and original digest; POST-after-commit lost ACK is reconciled by GitHub readback, not blind duplicate write. Changed payload with same identity is `CONFLICT`, later accepted correction cites the **actual** prior `corrects_ref`. Reader handles pagination, 429/backoff, stale source, duplicate/conflicting versions and unverifiable refs without false PASS or double count. An existing published comment whose body/digest differs from its immutable witnessed receipt, or whose actual edit metadata indicates unqualified in-place mutation, becomes `UNVERIFIED/CONFLICT` and **cannot** be current accepted evidence until independently reconciled; don't silently trust newest timestamp or overwrite prior immutable provenance. Any replacement uses a new versioned publication and current GitHub receipt, not mutation of historical PASS.

**D07 Privacy and scale.** Public GitHub only contains a bounded sanitized per-terminal Attempt Report plus material correction/learning when necessary; no raw prompts/secrets/private chain-of-thought/high-cardinality steps or arbitrary private Manifest contents. GitHub API costs and rate limits must be measured where relevant; no per-step Issue spam. **Sensitive-publication incident:** the owning authorized publisher must promptly remove/redact/minimize the exposed GitHub comment through actual GitHub permissions and record a **separate safe correction/revocation tombstone** (actual prior comment/source identity and reason, no leaked content), plus downstream invalidation/readback. These privacy-driven GitHub removals may override the default append-oriented history rule; preserve historical evidence privately when legally/safely permitted, but never promise deletion erases caches/forks. Consumers treat revoked/edited/unavailable reports as `UNVERIFIED` until authoritative repair; do not republish secrets in the tombstone.

**D08 Consumer feedback — product decision.** Tally publishes the distinct **`EXPERIENCE_USE_FEEDBACK` report profile within the same new v4 `kind: report` machine family** decided in D02; #1209 owns its specific contract in L2 and ADS GitHub publication semantics. It **does not** misuse `ai-dev:event-v2`, require task-meta's private `manifest_ref`/`manifest_sha256`, fabricate a Manifest, or create a separate feedback/event wire family. The v4 report's typed profile discriminator requires an immutable manifest/digest for a task-meta-owned execution summary, **but not** for a GitHub-native Tally usage-feedback publication; the latter carries actual GitHub receipt/source refs and self-declared actor/session, exact Task/Attempt/Procedure revision and verification/correctness limits. Tally publishes source-qualified `presented / accepted / applied / skipped / independently_checked / observed_effect` distinctions, with exact CI/Host references when truly witnessed, under stable report_id/revision and correction/readback rules. These are derived usage **observations**, not new canonical Task or Release Gate states; `APPLIED` is never proof of beneficial or validated effect.

**D09 Compatibility, qualified-but-untagged adoption and test-candidate identity — product decision.** A project may **explicitly adopt an immutable ADS commit integrated on `main` with source-bound `RELEASE_QUALIFICATION=READY`**, including the qualified untagged v4.14.0 `584512e8566408bed479192753c12a036309d277` with [RQ #1192](https://github.com/kaicreator-mm/ai-development-standard/issues/1192#issuecomment-6274752015), **without requiring an optional Tag or GitHub Release alias**. This is a project-local acceptance/upgrade checkpoint under `PROJECT_ADOPTION.md` §6, not automatic selection: require exact 40-character SHA, actual RQ/merge readback, source/wire/behavior/actor-authority/Task-Gate compatibility, active Task-pin preservation and authorized project-local update. The pre-existing v4.12 **tag-and-GitHub-Release-requiring advisory selector** remains unchanged and legitimately returns `NO_SAFE_RECOMMENDATION` for an untagged version; that refusal is **not** an automatic-vs-manual adoption veto. A bounded v4.15 normative documentation clarification is required to make the *manual exact qualified SHA path* unambiguous. Changing the old selector is **not** required for v4.15 and may be handled as a separately evidenced concern if proven necessary. An unqualified SHA, floating `main`, mere semver, unreviewed branch head, or incompatible release remains disallowed as an effective project pin.

**No circular E2E acceptance:** For J1–J6 before v4.15 Release Qualification, both real systems execute the **exact frozen v4.15 candidate SHA as an isolated validation/test subject**, with explicit validation configuration/receipt and code/contract currentness. It is **not** an effective production `.dev-standard/VERSION` adoption, does not silently override existing project pins or live Claims, and is invalidated by material candidate change. E2E evidence contributes *to* v4.15 qualification; **only after** qualified final version/main integration may each external project elect a separate version-compatible exact-SHA **effective adoption**. L2 must specify how test-mode candidate resolution is isolated from effective live task authority. This sequencing preserves release qualification rather than requiring its outcome as its prerequisite.

**D10 Real integration requirement and accepted delivery risk.** Source-schema conformance alone cannot close this version's **E2E acceptance**. Require an actually running supported Agent source adapter, actual task-meta Publisher, actual GitHub Issue comment/readback, and an actual Tally GitHub-only reader built/tested in its own repo. A focused minimal reader/vertical slice is enough; full Tally v2 Product delivery, all Agent adapters or Domain Package evolution are not prerequisites. **Accepted cross-repository schedule/dependency risk:** as verified by R0 Reviewer, task-meta has no implementation code yet and the Tally v2 TypeScript reader/DomainHarness application is Product/L2-only; neither is currently runnable. Task-meta and Tally owners must independently accept/build a bounded E2E-capable slice and publish actual source/evidence refs. ADS can progress Product/L2 and source-level conformance independently, but **v4.15 full Release Qualification remains `BLOCKED/NOT_RUN`** while the required external real vertical slice is missing; no unilateral scope shrink to source-only, fictitious PASS or indefinite extra approval stage.

## 5. Non-goals / implementation separation

- No ADS-native Agent/Host management daemon, task-meta DB/collector, Tally TS app/DomainHarness Engine, universal Agent RPC, cross-project service proxy or model training.
- No private Task Report Manifest resolution by Tally; no new ADS Account/Owner credential Gate, Task/Gate state, Agent Event-v3 replacement or separate duplicate Task Learning schema. The required D08 feedback profile is **within the new versioned GitHub report family**, not another parallel record family.
- No rewriting frozen v4.14 files, retroactive migration of historical GitHub comments, or mandatory new Tag/GitHub Release if exact adopted source qualification can legally be proved.
- No implementation of all Claude Code/Codex/ZCode hooks as the v4.15 acceptance floor: one real supported Agent is sufficient, other adapters remain project-local.
- No automatic Experience→Domain Package BUILD or uncontrolled Harness² probe recursion in this version.
