# v4.7 Authority / Applicability Manifest Registry — discovery reference

Owner: `standard-manifest.json` (`semantic_authorities`, additive and optional). Entry contract: `schemas/authority-applicability-entry-v1.schema.json` (T01). This is a *bounded discovery index*, not new normative authority and not a new execution resolver. The existing top-level `schema_version: 1` and the full legacy `sections` inventory remain intact. Historical consumers can continue to read `sections` without processing `semantic_authorities`.

Each entry identifies one tightly named `semantic_concern`, one `canonical_owner_ref` already present in `sections.normative_standards`, and a qualified `applicability_posture` from the T01 schema (`ALWAYS`, `MATERIALITY_DRIVEN`, `OPTIONAL`, `PROJECT_DEFINED`). Its `entry_id` is stable discovery identity, **not** an authorization principal. The finite initial set intentionally indexes only normative owners already present in this version's manifest. Owners or semantics still confined to separate v4.1–v4.6 version branches must not be claimed as currently integrated. Missing entries are not evidence of non-applicability; consult the authoritative owner and current pinned standard.

`compatibility_alias_refs` are one-hop pointers from existing `sections.compatibility_entries` to the entry's existing normative owner. They do not make the compatibility file a second owner. Some historical entry files mention **multiple** standards; a scoped alias in this index only routes the corresponding named concern and must not erase other references in that historical file. An alias may not be an owner, point at another alias, or be assigned to two semantic concerns in this bounded mapping. Broken paths, duplicates, ambiguous competing owners and attempted alias chains/cycles fail closed. No order-based fallback is permitted. `applicability_refs` and `notes_ref`, when present, are discovery pointers, not independent authorization.

`PROJECT_DEFINED` and `OPTIONAL` never mandate adoption by registry presence. Even `ALWAYS` describes discovery posture; actual applicability and all permitted side effects come from the pinned normative owner, Frozen Product/L2, actual Task Pack allowed write-set, live GitHub Issue Dependencies, and the exact-currentness Validation/Review/Merge gates. A provider's credentials or availability and a row in this manifest **never authorize** file mutation, PR merge, external side effect, a PASS verdict or Release READY.

Deterministic checks: `python scripts/test_v47_authority_registry.py`; then standard protocol/verifier and repository regression in a fresh checkout of the **same** PR HEAD. The focused test executes the merged T01 schema's closed entry constraints, resolves owner and alias paths against the real manifest/checkout, exercises duplicate owner independent of entry order, missing owner/alias/ref, rejected alias chain/cycle shapes, invalid applicability and attempted mutation/merge/release-grant fields. This focused script is executable conformance evidence only, **not** a live permission engine and not a substitute for an independent clean `LOCAL_VALIDATOR` or a genuinely NEW read-only Fresh Reviewer. Its reference to the initial historical inventory does not freeze all future additive `sections` changes; authorization remains with the owning change.
