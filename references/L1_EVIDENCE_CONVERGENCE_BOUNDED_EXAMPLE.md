## Multi-study Product L1 example (app8-inspired, hypothetical snapshot)

Product question: Is there sufficient evidence to recommend this proposed category? The same project has several source-qualified experiment protocols, but real blind/cross-host evidence is not yet executed. The table shows how to stop recursive infrastructure hardening and distinguish project evidence from tooling CI.

| L1 node | Dependencies | Actual evidence state | Blocking class | Minimal next evidence / executor |
| --- | --- | --- | --- | --- |
| A: freeze protocol+input | none | source protocol reviewed | none | source-bound immutable protocol / Web |
| B: obtain independent gold | A | NOT_RUN | EXECUTION_BLOCKER if no authorized human/independent generation available | real reference data, independent procedure |
| C: blind evaluation | A, B | NOT_RUN | dependency on B | execute real study in selected Host context |
| D: optional dashboard polish | A | incomplete | OPTIONAL_HARDENING | defer; does not block B/C |
| E: reusable production experiment service | separate L2/Product decision | NOT_STARTED | IMPLEMENTATION_CONCERN | do not promote to L1 prerequisite |

**Negative 1:** 7/7 study *protocol PRs* merged while 0/7 actual study results executed is not a study PASS. Product Freeze remains unproven until actual required results and Product authority decision.

**Negative 2:** an optional dashboard retry/review finding has no demonstrated effect on blindness, exact source or scoring validity. Classify `OPTIONAL_HARDENING` and proceed to B/C; do not create a permanent L1 gate or repeat full CI. A discovered test-control leak affecting blindness is `EVIDENCE_VALIDITY_BLOCKER` and remains blocking.

**Negative 3:** Full Product review or Phase-2 Task DAG cannot be minted from the row snapshot; the existing `DEVELOPMENT_WORKFLOW.md` controls phase authority and GitHub live implementation Task dependencies.
