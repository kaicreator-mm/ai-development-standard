# v4.7 State-Dimension Registry Reference

**Non-normative reference.** The normative owner for each dimension is the owner identified in `registries/state-dimensions-v1.json`, subject to that owner's real currentness and adoption. This registry is metadata, not a live state store, state reducer, transition authorization, inference engine, or a source of Validation/Review/Release/Deployment verdicts. `schemas/state-dimension-registry-v1.schema.json` defines its data shape; the Frozen T03 Task Pack limits this concern to the registry, this reference, and its focused test.

## Ownership boundaries

Each `dimension_id` qualifies an independent claim, even where two owners use identical strings such as `PASS`, `READY` or `BLOCKED`. `vocabulary_posture` is **about the owning contract**, not permission for this registry to define or close its vocabulary. `CLOSED` means the identified owner provides a bounded vocabulary at the pinned/current source; `OWNER_DEFINED` means no enum is imposed here. Consumers MUST re-read actual owning authority; this JSON alone is not a permission or a validation report.

Local owner examples are the Work Item Contract Standard (Issue workflow), Execution Architecture Standard (Dispatch and owner-scoped Review orchestration), Execution Pack Standard (pack currentness), Validation Standard (actual Gate results), Release Standard (candidate and qualification), and CI Runner Capability Standard (observed routing capability). A declared runner capability does not prove current preflight, Task authorization, or successful Validation. A state value without `dimension_id` and exact subject/tuple is ambiguous and must not be elevated across owners.

The `forbidden_inferences` entries are explicit **prohibitions only**. They neither license unlisted inferences nor allow propagation of an old PASS to a different SHA, environment, profile, owner, or stage. Two rules deliberately have the same source and target dimension (`validation_gate`); their prohibited transition is across **materially different subjects**, not across state-machine dimensions. Actual evidence currentness and owner-specific gate rules remain authoritative.

## Upstream owner posture

Deployment uses the exact pinned `v4.4` version-branch commit containing the Deployment Governance owner and its result schema. That is an **upstream-qualified pointer**, not a claim that v4.4 has been imported into the current v4.7 branch, nor proof of a production deployment. If the pinned bytes/authority are inaccessible or an owner amendment is required, consumers return unresolved and route to the owning version rather than substitute a mutable version label.

`runtime_health` historically pointed to the frozen v4.5 L2 owner placement at commit `2acf8bb020d76d6bb90bcfbb0bf1580e2d2f20ea` (`docs/implementation/4.5.0/L2_ARCHITECTURE_EVIDENCE.md`); that Frozen L2 remains **historically valid conceptual provenance** for the dimension's design placement, but it is not the current normative owner. The actual separately merged immutable normative owner is `version/v4.5.0@c9ee9249999aa5463ce880bc7674b732979009b3:standards/OBSERVABILITY_RUNTIME_EVIDENCE_STANDARD.md` (blob `3dddb3b5b81f44491b198a5496ba70f64942a561`), and the registry now pins exactly that tuple. That owner file is **NOT imported into the local v4.7 branch**: the pointer is an upstream-qualified cross-version reference, and this branch's discovery metadata, not local normative inclusion. The normative owner's semantics (runtime evidence structure, separable signal categories, and its own `DEPLOYMENT_SUCCEEDED -> RUNTIME_HEALTHY` prohibition) are **qualified-available** through the immutable pin for cross-version reading, while actual external runtime observations, conformance, and integration against that owner are **NOT_RUN** in this repository and cannot be claimed from this registry. Consumers must fail closed on owner pin/currentness: if the pinned commit, path, or blob is inaccessible or a future owner amendment is required, return unresolved and route to the owning v4.5 version rather than substituting a mutable version label or the older conceptual L2 provenance. The entry therefore remains a known, owner-qualified dimension, not an active local normative Runtime vocabulary, an executable runtime-health evaluator, or a live state store; its posture is `OWNER_DEFINED`, not a fabricated closed `HEALTHY` enum. Consistent with F05, a recorded Deployment SUCCESS does not prove Runtime health, and neither a Frozen L2 pointer nor an upstream standard file name is permission to grant runtime or mutation authority; historical records cannot be retrofitted to PASS by a later registry update. This is a version branch boundary: the v4.5 normative owner, its actual external runtime observations, its executed conformance, and any future change to that owner must be separately verified by T07 and Version Closure against the live upstream branch before stronger local conformance or health claims.

## Reading and conformance

Resolve every rule's dimension IDs against unique entries. Resolve local `canonical_owner_ref` to a real repository file, and immutable upstream references to the exact pinned source where available. A missing/broken local ref, conflicting owner, stale external pin, unknown dimensional vocabulary, or ambiguity must fail closed; discovery order is not a tie-break. A forbidden rule that points to an unresolved external owner may still be recorded as an explicit non-inference invariant, but MUST NOT be used to claim that owner's local integration or executed coverage passed. Verify the exact source/target *subject* and owner before considering evidence.

Mandatory examples: Task `state:done` never implies Validation `PASS`; Review `PASS` never implies Validation `PASS`; Validation `PASS` never implies Release `READY`; Release `READY` never implies Deployment `DEPLOYMENT_SUCCEEDED`; Deployment success never proves Runtime health; observed tool availability never authorizes file writes or side effects; an old exact-SHA Validation `PASS` cannot be transferred to a successor SHA; sandbox Validation `PASS` cannot be transferred to an unexecuted real environment. Likewise, Dispatch `COMPLETED` does not imply Release `READY` and Execution Pack `PACK_CURRENT` does not prove Validation `PASS`.

This dataset is not a global PASS/READY/BLOCKED enum. Do not use it to write or rewrite owning state machines, introduce new workflow transitions, close T03 itself, manufacture Validation/Review/Release/Deployment status, or assert upstream incorporation. T07 must independently test any future registry population/currentness and the full v4.1–v4.6 integrated conformance after their actual merged authorities are available.
